Take a Windows executable, read it as a sequence of bytes, lay the bytes out as pixels, and train an image classifier on the result. That is the whole idea behind image-based malware classification, and on the standard benchmark it reaches 97 to 99% accuracy. The first version of this post built exactly that, a ResNet50 on the Malimg dataset, and reported "85 to 90% test accuracy" without having measured it. This version starts over from what a file is, measures everything it claims, and tries to explain each step well enough that you could have designed it yourself.

Here is the chain of reasoning the post follows. An executable is a byte string. A malware family is a set of files produced by one build process: the same source, compiler, linker and packer, run over and over with small changes. Classifying a file into a family therefore means finding properties of the byte string that the build process leaves fixed and the changes leave alone. A byteplot is one particular way of exposing such properties to a model that was designed for photographs, and the question underneath every result below is which properties it exposes, which it hides, and which of the exposed ones are actually about the malware rather than about the toolchain or the benchmark.

Measured on Malimg: a classifier that sees only the image's width and height gets 90.6%; the ResNet50 gets 97.3%; a nearest-neighbour lookup on a 32×32 thumbnail gets 98.0%; and 82.5% of a random test set has a near-identical copy in the training set. The rest of the post explains where each of those numbers comes from, what the network is attending to (from the papers that looked), why the approach breaks on real detection (packing, time, adversarial bytes), and what the 2025 and 2026 work does about it. Every diagram is taken from a paper and says which. The experiment code is short and linked at the end.

## From bytes to pixels

A PE file is a byte string. Nataraj, Karthikeyan, Jacob and Manjunath proposed in 2011 [\[1\]](#ref-1) to read it as unsigned 8-bit integers, choose a width from the file size, wrap the string into rows of that width, and treat the result as a grayscale image. Their width table:

| File size | Image width |
|---|---|
| under 10 kB | 32 |
| 10 to 30 kB | 64 |
| 30 to 60 kB | 128 |
| 60 to 100 kB | 256 |
| 100 to 200 kB | 384 |
| 200 to 500 kB | 512 |
| 500 to 1000 kB | 768 |
| over 1000 kB | 1024 |

_Table 1. Byteplot width as a function of file size, from Nataraj et al. [\[1\]](#ref-1). Height is file size divided by width. Note what this implies: the image's dimensions are a deterministic function of file size, and file size is a family feature._

The whole conversion is a reshape:

```python
import numpy as np
from PIL import Image

WIDTHS = [(10_000, 32), (30_000, 64), (60_000, 128), (100_000, 256),
          (200_000, 384), (500_000, 512), (1_000_000, 768), (float("inf"), 1024)]

def byteplot(path):
    raw = np.fromfile(path, dtype=np.uint8)          # every byte is a pixel value 0..255
    width = next(w for limit, w in WIDTHS if raw.size < limit)
    rows = raw.size // width                          # the last partial row is dropped
    return Image.fromarray(raw[: rows * width].reshape(rows, width), mode="L")
```

It helps to be precise about what this conversion keeps and what it throws away. Reshaping is a bijection on the bytes it keeps: the image contains exactly the byte values of the file, in order, minus the partial last row. So nothing is lost, and nothing is added either. The header is not interpreted, the sections are not located, no instruction is decoded; whatever the model finds later was already present as a pattern in the raw byte sequence. What the two-dimensional layout contributes is only an assumption about neighbourhood: that byte $$i$$ is related to byte $$i+1$$ (true, for most of a file) and to byte $$i + \text{width}$$ (true only when the file has a periodic structure whose period divides the width). Keep that in mind, because every strength and every weakness of the method traces back to it.

Each pixel is one byte: 0x00 is black, 0xFF is white, and the values in between are shades of grey. That mapping gives every part of an executable a texture. Runs of zero padding are black bands. ASCII strings are a narrow mid-grey band, because printable characters live between 0x20 and 0x7E. Machine code is a fine-grained noise with a few bright recurring values, the common opcodes and register encodings. Compressed or encrypted data is uniform noise with no structure at any scale, because a good compressor leaves close to eight bits of entropy per byte. The banner of this post is a real executable, `/bin/ls`, rendered this way and tinted. You can read it without a model. The sparse dotted region at the top is the ELF header and section headers: mostly zero bytes with small integers. The regular vertical stripes are a table with a fixed record stride, the symbol table. The dense noise at the bottom is machine code, which has no periodicity a byteplot can show. A PE file has the same kind of anatomy:

![PE file structure](/assets/img/malware-cnn/ember_pe_structure.png)
_Figure 1. The 32-bit PE file layout, from the EMBER paper [\[2\]](#ref-2) (Creative Commons image). Headers, section table, then sections: code, initialized data, imports, resources. Each has a characteristic byte distribution, and each shows up as a band in the byteplot._

Reading Figure 1 top to bottom gives you the bands of a PE byteplot. The file opens with the DOS header, two bytes `MZ` and a 16-bit stub program that prints "This program cannot be run in DOS mode", then the PE signature and the COFF header: machine type, number of sections, a compile timestamp. The optional header follows with the entry point address, the image base, the section alignment, and the data directories that point to the import and export tables. Then comes the section table, one 40-byte record per section, giving each section's name, its offset and size on disk, and its address in memory. Sections start on disk at multiples of the file alignment, usually 512 bytes, so the gap between the end of one section's data and the next boundary is zero-filled. Those gaps are the black bands.

The sections themselves have recognizable textures. `.text` holds machine code and looks like fine noise with a few frequent bright values. `.rdata` holds read-only data including the import address table, a list of 4- or 8-byte pointers whose high bytes repeat, which gives a fine vertical stripe. `.data` is mostly zeros with scattered initialized values. `.rsrc` holds icons, dialogs and version strings; icons are uncompressed bitmaps and look like small pictures, strings look like the mid-grey ASCII band. A packed section, discussed in Section 7, looks like none of these: uniform noise edge to edge.

MalNet's authors drew the same correspondence for Android DEX files:

![DEX structure and its byteplot](/assets/img/malware-cnn/malnet_dex_structure.png)
_Figure 2. Left, the DEX file structure (header, ids, data). Right, the byteplot of the same file. From Freitas, Duggal and Chau, MalNet [\[3\]](#ref-3)._

The DEX case is cleaner than PE because the `ids` region is a set of tables with fixed record sizes, 4 bytes per string id, 8 per method id, 12 per field id, and a row-wrapped table with a fixed stride produces vertical stripes whenever the row width is a multiple of the stride, and a diagonal texture otherwise. That is the vertical structure a 2D convolution can use, and it is an accident of the width rule whether it appears as stripes or diagonals.

Two families side by side make the point that a family shares layout, not just bytes. Here are three families under the plain grayscale transformation, from a 2025 San José State study that compares nine such transformations [\[4\]](#ref-4):

![Grayscale byteplots of three families](/assets/img/malware-cnn/sjsu_grayscale.png)
_Figure 3. Grayscale byteplots of samples from the Agensla, Convagent and Crypt families. From Stamp's group at SJSU [\[4\]](#ref-4). Within a family the band structure repeats; between families it differs._

The repetition inside a family has a mundane cause. Members of a family are built from the same source with the same compiler and linker, so they have the same sections in the same order, the same imports, the same embedded resources, and often the same size to within a few kilobytes. A polymorphic engine that re-encrypts the payload on every infection changes the bytes of one section and leaves the layout alone. That is why layout is a family signature and also why it is a weak malware signature: benign programs built with the same toolchain share the same layout.

### What a convolution sees here, and what it does not

A 2D convolution assumes that pixels near each other in both directions are related. In a byteplot, horizontal neighbours are adjacent bytes; vertical neighbours are bytes one row-width apart, and the row width was chosen by a lookup table, not by the file's structure. Raff and colleagues, who built MalConv to read the raw byte sequence directly, drew what a receptive field on a byteplot corresponds to in the file:

![Receptive field of a convolution mapped back to the byte stream](/assets/img/malware-cnn/malconv_receptive_field.png)
_Figure 4. A square receptive field on the byteplot (top) maps to three disjoint stretches of the byte sequence (bottom), separated by the row width. From Raff et al., MalConv [\[5\]](#ref-5). The vertical dimension of the image is an artefact of the wrapping._

This does not make byteplots useless. Tables with a fixed record size produce real vertical structure, as the banner shows, and section boundaries produce horizontal bands regardless of width. What the first convolutional layer learns on this input is therefore a set of horizontal edge detectors, which fire at section boundaries, and a set of periodic detectors, which fire on table strides. The deeper layers combine them into a description of which bands appear in which order and at which relative positions. That is a layout descriptor, and the rest of this post is about what a layout descriptor can and cannot do.

The image prior is only partly right, and the alternatives people have tried are attempts to fix it. A Hilbert curve maps the 1D byte stream onto a 2D grid so that consecutive bytes are always adjacent and any contiguous run of bytes becomes a compact blob rather than a strip cut across rows [\[4\]](#ref-4); a section becomes a region, and the row width stops mattering. An entropy map replaces each block of bytes, typically 256 or 1024 of them, by its Shannon entropy in bits, so the image encodes "how compressed is this region" instead of the bytes themselves; code and tables land in the middle of the range and packed or encrypted data saturates at the top [\[4\]](#ref-4), [\[6\]](#ref-6). MalConv reads the bytes as a sequence with no image at all [\[5\]](#ref-5); Section 8 explains how.

![Hilbert curve](/assets/img/malware-cnn/sjsu_hilbert_curve.png)
_Figure 5. A second-order Hilbert curve. Consecutive positions along the curve are adjacent in the plane, which a row-wrap does not guarantee. From [\[4\]](#ref-4)._

![Hilbert-curve byteplots](/assets/img/malware-cnn/sjsu_hilbert.png)
_Figure 6. The same three families under a Hilbert-curve layout with a byte-class colouring. From [\[4\]](#ref-4). In that study, grayscale, byte-class and Hilbert layouts scored within a few points of each other; entropy and bigram transformations scored slightly lower._

## The toolkit

Four pieces of machinery are enough to understand the experiment, and each can be motivated from a small assumption rather than taken on faith. Convolution follows from two beliefs about images. The receptive-field arithmetic tells you what a resize does before the network sees anything. Softmax with cross-entropy is what you get if you insist on probabilities. And transfer learning is a bet that the early layers of a network trained on photographs are useful for anything made of edges and textures.

### Convolution and its arithmetic

A convolutional layer with kernel $$K \in \mathbb{R}^{k \times k}$$ applied to an input $$X$$ computes, at output position $$(i, j)$$,

$$
(X \ast K)_{ij} = \sum_{u=0}^{k-1}\sum_{v=0}^{k-1} X_{i+u,\, j+v}\, K_{u,v} + b.
\tag{1}
$$

Deep learning frameworks call this a convolution; it is a cross-correlation, since the kernel is not flipped. For an input of side $$n$$, padding $$p$$ and stride $$s$$, the output side is

$$
n_{\mathrm{out}} = \left\lfloor \frac{n + 2p - k}{s} \right\rfloor + 1,
\tag{2}
$$

and a layer with $$c_{\mathrm{in}}$$ input channels and $$c_{\mathrm{out}}$$ output channels has $$c_{\mathrm{out}}\,(c_{\mathrm{in}} k^2 + 1)$$ parameters. The first layer of ResNet50 is a $$7 \times 7$$ kernel with stride 2 over 3 channels into 64: $$64 \cdot (3 \cdot 49 + 1) = 9{,}472$$ weights, independent of the image size. A fully connected first layer on a $$224 \times 224 \times 3$$ input into 64 units would need $$9.6$$ million. Why this operator and not another? Two beliefs force it. The first is locality: a pixel interacts directly only with its neighbours, so each output should depend on a small window of the input. The second is translation equivariance: a pattern means the same thing wherever it occurs, so the same weights should be used at every position. Locality gives you a small kernel; equivariance gives you weight sharing; together they give you equation (1), and the parameter count drops from millions to thousands as a consequence rather than as a design goal. Both beliefs are exactly right for photographs. For a byteplot the first is right along a row and questionable down a column, and the second is right for textures but wrong for the header, which means something different from the same bytes anywhere else in the file. Figure 4 is what those two caveats look like.

### Receptive field

Stacking $$L$$ layers of kernel $$k$$ and stride 1 gives each output unit a receptive field of side $$1 + L(k-1)$$; a stride-$$s$$ layer multiplies the growth of all later layers by $$s$$. ResNet50's final feature map has a receptive field larger than a $$224$$ input, so every output feature depends on the whole image. Resizing a $$384 \times 424$$ byteplot to $$75 \times 75$$, as the original tutorial did, means each input pixel already averages about 29 bytes before the first convolution sees it. Bilinear resizing is a low-pass filter: it keeps the bands, the black padding regions, and the mean brightness of each section, and it destroys everything at the byte scale, including the opcode texture and the table strides. What survives the resize is exactly the layout information, which is why a network fed $$75 \times 75$$ inputs learns layout.

### Softmax and cross-entropy

For logits $$z \in \mathbb{R}^C$$ and true class $$y$$,

$$
p_c = \frac{e^{z_c}}{\sum_{c'} e^{z_{c'}}}, \qquad \mathcal{L} = -\log p_y.
\tag{3}
$$

Where does this form come from? You want to turn $$C$$ unconstrained scores into a probability distribution and then reward the probability assigned to the right answer. Exponentiating makes every score positive, dividing by the sum makes them add to one, and among all ways of doing that the exponential is the one that assumes the least beyond the scores themselves. Rewarding the log of the probability, rather than the probability, makes a confident wrong answer cost much more than an unsure one. The gradient with respect to the logits works out to $$p - e_y$$: push the true class up, push every other class down in proportion to how much probability it currently gets.

Notice what this does and does not optimize. It trains calibrated probabilities, not accuracy, and it treats every training image as equally important. On a dataset where one class is a third of the data, the gradient is dominated by that class, and the network can reach a high accuracy while being poor on the small classes. The usual correction is a per-class weight in the loss, $$w_c = N / (C\, n_c)$$ for $$n_c$$ samples of class $$c$$ among $$N$$ total, which makes each class contribute equally to the gradient on average. The original tutorial trained with unweighted cross-entropy on a dataset where one class is 32% of the data. The same reasoning is why the experiment below reports macro-F1 next to accuracy: if the loss did not weight the classes equally, the metric has to.

### Transfer learning

Freeze a network pretrained on ImageNet, replace its last layer with a $$2048 \to C$$ linear map, and train only that map. Because the backbone never changes, you can run it once over every image, cache the 2048-dimensional outputs, and train the head on the cache. That is exactly what the experiment below does; it is the tutorial's model, and it is why the whole thing runs on a CPU in minutes. The transfer works at all because early ImageNet filters are generic edge and texture detectors, and a byteplot is made of edges and textures. It works less well than it could because the later filters encode object parts that byteplots do not contain, and because the features are computed at a resolution where the byte-level texture is already gone. Fine-tuning the last block recovers some of that; the MalNet-Image Tiny ablation in Section 8 puts numbers on it.

## The dataset

Malimg [\[1\]](#ref-1) has 9,339 byteplots from 25 families, collected in 2011. It is the benchmark on which nearly every image-based malware paper reports, and it has three properties you need to know before you read any number from it.

**It is imbalanced.** Two variants of the Allaple worm account for 4,540 of the 9,339 images. The two smallest families, Skintrim.N and Wintrim.BX, have 80 and 97.

![Malimg class distribution](/assets/img/malware-cnn/malimg_class_distribution.png)
_Figure 7. Malimg samples per family, from a 2023 study of imbalance in byteplot classification [\[7\]](#ref-7). The same paper found that heavier imbalance makes models converge in fewer epochs and increases the variance between models, and reported precision of up to 97% on Malimg with ResNet50, EfficientNetB0 and DenseNet169._

**It is nearly solved by nearest neighbours.** Nataraj et al.'s own 2011 result was 98% with GIST texture features and $$k$$-NN. GIST summarizes an image by the energy of oriented filters in a coarse grid of cells, which for a byteplot means "which bands are where and how textured they are", the layout descriptor again. A CNN that scores below that is not extracting anything the 2011 method missed. The size table above already predicts part of the result: in the version of the dataset used below, three families (Autorun.K, Obfuscator.AD, Yuner.A) occupy a single (width, height) shape and six occupy three or fewer, so those families are identified by file size before any pixel is read. Figure 10 lists the count for every family.

**Its families are near-duplicates at the byte level.** A 2024 study of packing recovered 8,263 of the original binaries and clustered them by two fuzzy hashes, ssdeep and TLSH. The clusters are the families:

![Malimg clustered by fuzzy hashes](/assets/img/malware-cnn/packing_malimg_clusters.png)
_Figure 8. Malimg binaries clustered by TLSH distance under 100 and ssdeep similarity over 70; only clusters with more than 10 members are drawn. From Assessing the Impact of Packing on ML-based Malware Detection [\[8\]](#ref-8). In the authors' words, "the files of each family are similar at the byte level"._

Fuzzy-hash similarity is what a signature engine uses. If a family's members are within ssdeep distance of each other, a random train/test split places near-copies of each test file in the training set, and any classifier with a memory scores well. The experiment measures how much.

## The experiment

I merged the three folders of a public Malimg mirror back into one set of 9,339 images across 25 families and ran three classifiers under two splits. The code is [`malimg_exp.py`](/assets/code/malimg_exp.py); the per-family numbers are in [`malimg_summary.json`](/assets/code/malimg_summary.json).

**Three classifiers.**
1. *Size only.* 1-nearest-neighbour on two numbers: image width and height. By Table 1 this is a classifier on file size, with a coarse quantization.
2. *Pixels.* 1-nearest-neighbour on the image downsampled to $$32 \times 32$$.
3. *The tutorial's model.* ResNet50 with ImageNet weights, frozen, input resized to $$75 \times 75$$ and replicated to three channels, a linear head trained with Adam for 40 epochs on the cached features.

The third classifier is what the original tutorial built, restated so that the frozen backbone runs once:

```python
import torch, torchvision
net = torchvision.models.resnet50(weights="IMAGENET1K_V1"); net.fc = torch.nn.Identity(); net.eval()
mean = torch.tensor([0.485, 0.456, 0.406]).view(1, 3, 1, 1); std = torch.tensor([0.229, 0.224, 0.225]).view(1, 3, 1, 1)

with torch.no_grad():                                 # one pass, 9,339 images, 220 s on a CPU
    feats = torch.cat([net((torch.tensor(b)[:, None].repeat(1, 3, 1, 1) - mean) / std)
                       for b in np.array_split(im75, 74)]).numpy()      # im75: (N, 75, 75) in [0, 1]

head = torch.nn.Linear(2048, 25); opt = torch.optim.Adam(head.parameters(), lr=1e-3)
X = torch.tensor(feats); X = (X - X[tr].mean(0)) / (X[tr].std(0) + 1e-6)   # standardize with train statistics only
for epoch in range(40):
    for b in torch.randperm(len(tr)).split(64):
        i = torch.tensor(tr)[b]
        loss = torch.nn.functional.cross_entropy(head(X[i]), torch.tensor(y)[i])
        opt.zero_grad(); loss.backward(); opt.step()
pred = head(X[te]).argmax(1)
```

With the backbone frozen, the only trainable part is the final linear map, and the input to that map for a given image never changes. So "training a ResNet50" here means computing each image's 2048-dimensional feature vector once and fitting a multinomial logistic regression on those vectors, which is what the code does. This is the tutorial's model, not a cheaper stand-in for it, and it is why anyone can rerun the experiment in about four minutes on a laptop with no GPU. The grayscale image is copied into three channels because the ImageNet weights expect RGB, and the normalization constants are ImageNet's channel means and standard deviations; the network was trained with them and behaves differently without them.

**Two splits.**
1. *Random.* Stratified 80/20 over images, which is what the tutorial and most papers do.
2. *Grouped.* Images whose $$8 \times 8$$ average-hash is identical are placed in one group, and groups are kept entirely on one side of the split.

The average hash is a coarse near-duplicate test. Downsample each image to $$8 \times 8$$, compute the mean, and write a 1 for each cell above the mean and a 0 otherwise; two images match when all 64 bits agree. It is invariant to file size and to small byte changes inside a section, and it is far weaker than ssdeep, which compares the actual byte content in a rolling window. Anything the hash groups together is close to a copy; plenty of things it keeps apart are still near-copies by ssdeep's standard.

```python
from sklearn.model_selection import train_test_split, GroupShuffleSplit

def ahash(im):                                        # 64-bit average hash
    small = np.asarray(im.resize((8, 8), Image.BILINEAR), dtype=np.float32)
    return (small > small.mean()).tobytes()

groups = np.array([group_id.setdefault(ahash(im), len(group_id)) for im in images])

tr_r, te_r = train_test_split(idx, test_size=0.2, stratify=y, random_state=0)      # what tutorials do
tr_g, te_g = next(GroupShuffleSplit(test_size=0.2, random_state=0).split(idx, y, groups))  # groups stay on one side

leak = np.mean([groups[i] in set(groups[tr_r]) for i in te_r])   # 0.825 on Malimg
```

A train/test split estimates how a model will do on new data only if the test images are independent of the training images. That is the assumption behind every accuracy number, and near-duplicates break it: if a test image has an almost identical twin in the training set, the test measures memory rather than generalization. `GroupShuffleSplit` restores the assumption at the group level by keeping every group entirely on one side. It cannot stratify by family at the same time, so the grouped test set has 1,468 images against the random split's 1,868 and its family proportions differ; the per-family numbers in the JSON are what to compare, not the totals. Even this coarse grouping found 895 byte-identical files and collapsed the 9,339 images into 2,033 groups, 1,552 of them singletons. Under the random split, 82.5% of test images have a near-duplicate in the training set: for four test images out of five there is a training image that reduces to the same 64 bits, and a nearest-neighbour rule only has to find it. Both nearest-neighbour classifiers use plain Euclidean distance with $$k = 1$$; the random split is stratified by family so every family appears in both halves; the ResNet head is trained on standardized cached features with a batch size of 64. Nothing is tuned on the test set.

| Classifier | Random split | Grouped split |
|---|---|---|
| Majority class | 31.6% | 28.7% |
| Size only, 1-NN on (width, height) | 90.6% | 82.1% |
| Pixels, 1-NN on 32×32 | 98.0% | 97.7% |
| ResNet50 frozen + linear head, 75×75 | 97.3% | 96.3% |

_Table 2. Accuracy on Malimg, 25 families, 20% held out. Macro-F1 for the same runs: size 0.80 / 0.49, pixels 0.95 / 0.93, ResNet 0.96 / 0.83. Accuracy counts correct images, so the two Allaple families decide it; macro-F1 is the mean of the per-family F1 scores, so each family counts once and a family that is always misclassified costs as much as Allaple would._

_Figure 9. The three classifiers under the two splits. This and Figure 10 are the only figures in this post that were made for it._

![Size-only accuracy per family](/assets/img/malware-cnn/exp_size_per_family.png)

Three things follow from the table, and each is worth explaining rather than just stating.

**Two numbers per image carry most of the signal.** Width and height alone reach 90.6% under the random split. Nataraj's width rule quantizes file size into eight bins and the height then encodes it exactly, so this is a file-size classifier. Families whose members are the same binary with small mutations share a size; the polymorphic Allaple variants, which dominate the dataset, are the clearest case.

**A thumbnail lookup beats the CNN.** 1-nearest-neighbour on a $$32 \times 32$$ downsample scores 98.0%; the frozen ResNet50 scores 97.3%. This is Nataraj et al.'s 2011 result, 98% with texture features and $$k$$-NN, reproduced with an even cruder feature. Why does something so simple work? Nearest-neighbour classification is optimal when each class forms a tight cluster and the distance you use respects the clusters, and Figure 8 is a picture of exactly that situation: within a family the byte content is close, so within a family the thumbnails are close, and the nearest thumbnail is almost always a family member. The thumbnail also contains the same information the ResNet receives, a low-pass version of the layout, so there is nothing for the network to add. The tutorial's "85 to 90%" sat below both, which is the kind of number you get when something in the pipeline is wrong; the resize to $$75 \times 75$$ with an unchecked split is the likely cause.

**Removing duplicates changes the macro-F1, not the accuracy.** Under the grouped split the ResNet's accuracy barely moves, 97.3% to 96.3%, but its macro-F1 falls from 0.96 to 0.83, and the size-only classifier's from 0.80 to 0.49. Accuracy is carried by the two Allaple variants, whose members are near-identical whether or not they share a hash; macro-F1 weights the small families equally, and those were being recognized through copies. The hash grouping is coarse, far weaker than the ssdeep clustering of Figure 8, so 96.3% is still an upper bound on what the benchmark can say about recognition rather than memory.

None of this is specific to my run. It is the reason MalNet's authors report macro-F1 rather than accuracy, and get 0.49 for type and 0.65 for family with a ResNet on 1.26 million images [\[3\]](#ref-3): a benchmark without near-duplicate families is a different problem.

## What the network looks at

Grad-CAM weights the last convolutional feature maps by the gradient of the class score and adds them up:

$$
L^{c} = \mathrm{ReLU}\Big(\sum_k \alpha_k^{c}\, A^{k}\Big), \qquad \alpha_k^{c} = \frac{1}{Z}\sum_{i,j} \frac{\partial y^{c}}{\partial A^{k}_{ij}}.
\tag{4}
$$

Here $$A^{k}$$ is the $$k$$-th feature map of the last convolutional layer, $$y^{c}$$ is the score for class $$c$$ before the softmax, and $$\alpha_k^{c}$$ is the average gradient of that score over the map, which measures how much the map matters for the class. The weighted sum, clipped at zero, is a coarse heat map at the resolution of the last layer, upsampled onto the input. In PyTorch it is two hooks and one line of arithmetic:

```python
acts, grads = {}, {}
layer = net.layer4                                           # last convolutional stage of ResNet50
layer.register_forward_hook(lambda m, i, o: acts.__setitem__("A", o))
layer.register_full_backward_hook(lambda m, gi, go: grads.__setitem__("dA", go[0]))

score = net(x)[0, c]; net.zero_grad(); score.backward()       # y^c for the class of interest
alpha = grads["dA"].mean(dim=(2, 3), keepdim=True)            # alpha_k^c: average gradient per map
cam = torch.relu((alpha * acts["A"]).sum(1, keepdim=True))    # equation (4)
cam = torch.nn.functional.interpolate(cam, size=x.shape[-2:], mode="bilinear")
cam = (cam - cam.min()) / (cam.max() - cam.min() + 1e-8)      # 0..1, overlay on the byteplot
```

For a $$75 \times 75$$ input, `layer4` has a $$3 \times 3$$ spatial extent, so the heat map has nine cells before upsampling; at $$224 \times 224$$ it has 49. That coarseness is inherent to the method and is why the overlays in the figures look like blocks. Applied to byteplots it shows where the evidence is:

![Grad-CAM on malware byteplots](/assets/img/malware-cnn/gradcam_grayscale.png)
_Figure 12. Grayscale byteplots and their Grad-CAM overlays, from an August 2026 comparison of explanation methods on malware images [\[9\]](#ref-9). The heat sits on band boundaries and on the header region, not on the code._

![Grad-CAM against HiResCAM](/assets/img/malware-cnn/gradcam_vs_hirescam.png)
_Figure 13. Grad-CAM and HiResCAM on the same samples, from [\[9\]](#ref-9). The authors found no explanation method that beat Grad-CAM on this data, and that feeding the overlays back as a second input channel improved accuracy; their best 17-family result was about 75%._

MalNet's attention maps tell the same story at scale: ransomware and trojans draw attention to a thin part of the data section, benign apps to a wide range of it, adware to the header [\[3\]](#ref-3).

![MalNet attention patterns](/assets/img/malware-cnn/malnet_attention.png)
_Figure 14. Attention patterns across four malware types, two samples each, from [\[3\]](#ref-3)._

The network is reading layout: where sections start, how long the tables are, what the header says. "What the header says" is concrete: the section count, the entry point, the linker version and the compile timestamp are bytes in the first kilobyte, and within a family they are constants or near-constants. Those are also the bytes a packer rewrites and an adversary can edit freely.

## Why this does not transfer to detection

Family classification on a fixed benchmark is one task. Deciding whether a new file is malicious is a different one, and three things break on the way.

### Packing

A packer compresses or encrypts the original program, stores the result as data, and prepends a small stub that decompresses it into memory and jumps to it at run time. The file on disk has the packer's layout, not the program's: the stub's code section, then one large section whose bytes are the compressed payload. Compressed data is close to eight bits of entropy per byte, so the byteplot of a packed file is a small header, a small stub, and a large block of uniform noise, whatever the original program was. UPX, the most common packer, is used by a large share of legitimate installers. The layout features above are gone. Packing is not a malware signal, either: in the dataset used to train ViPER, 76% of malware and 73% of benign files were packed [\[10\]](#ref-10).

![Packing prevalence in malware](/assets/img/malware-cnn/viper_packing_malware.png)
_Figure 15. Packing label distribution among malware samples in the ViPER dataset, from [\[10\]](#ref-10). Benign software is packed at nearly the same rate._

The 2024 packing study trained detectors including a ResNet on unpacked files and tested on packed ones:

![Detectors trained without packed files, tested on packed and unpacked](/assets/img/malware-cnn/packing_boxplot_unpacked_training.png)
_Figure 16. Performance of ML malware detectors trained without packed executables, evaluated on packed and unpacked test sets. From [\[8\]](#ref-8). The authors warn that with packed families that the classifier may "learn to classify packers instead of malware"._

### Time

Every held-out accuracy is a forecast, and a forecast is only as good as the assumption that tomorrow's files are drawn from the same distribution as today's. Malware is the one domain where that assumption fails by construction, because the people generating the distribution are trying to get past the classifier. So a classifier trained on 2014 samples and tested on 2018 samples is a different experiment from one tested on a random 20% of 2014, and only the first one estimates what deployment will look like. TESSERACT [\[11\]](#ref-11) measured this on Android malware. Their metric, area under time, is the average of the monthly $$F_1$$ over the test period, so it rewards a detector that stays good, not one that starts good. Two detectors that report $$F_1$$ near 0.99 under a random split scored an AUT of 0.50 and 0.49 when trained on 2014 and tested month by month through 2018:

![Performance decay over time](/assets/img/malware-cnn/tesseract_time_decay.png)
_Figure 17. Time decay of two Android malware classifiers, DREBIN and a deep model, trained on 2014 and tested through 2018. From TESSERACT [\[11\]](#ref-11)._

EMBER, the standard static-PE dataset, ships with a time-based split for exactly this reason [\[2\]](#ref-2):

![EMBER temporal distribution](/assets/img/malware-cnn/ember_temporal.png)
_Figure 18. EMBER's monthly sample distribution; the last two months are the test set. From [\[2\]](#ref-2). On this split a default LightGBM on hand-designed features scored ROC AUC 0.99911 and MalConv on raw bytes 0.99821._

The decay has several sources at once. New families appear and old ones stop being distributed. Existing families move to new packers and new toolchains, which changes their layout without changing their behaviour. The benign side drifts too, as operating systems and compilers change what a normal program looks like. And labels arrive late: a sample's family is often known only months after it was first seen, so a detector trained on "everything labelled by January" was trained on last year's malware. A 2025 follow-up shows the decay is largely the arrival of new families: in one dataset the fraction of test malware belonging to families seen in training falls steadily year over year [\[12\]](#ref-12). Malimg has 25 families fixed in 2011. It cannot measure this at all.

### Adversarial bytes

A PE file has room in it that the loader never reads: most of the DOS header after the first two bytes and the offset to the PE header, the slack between the end of one section and the alignment boundary of the next, and anything appended after the last section. Bytes written there change the file and the byteplot without changing what runs. Think of it in terms of the input space. The classifier is a function of the whole byte string, but only some directions in that space change the program's behaviour; the loader-ignored bytes span directions that are free. An attacker who can compute the gradient of the malware score with respect to the input, or estimate it by querying, walks along the free directions until the score crosses the threshold, and the result is a file that runs identically and is classified differently. Because those directions exist in every PE file and the walk costs a few hundred gradient steps, evasion is cheap. Kolosnjaji et al. appended 10,000 padding bytes, under 1% of the input, chosen by gradient, and cut MalConv's accuracy by more than half [\[13\]](#ref-13). Demetrio et al. generalized this to edits inside the header and between sections that keep the program running, and evaded most detectors they tested by changing about 2% of the bytes [\[14\]](#ref-14):

![Locations of adversarial manipulations in a PE file](/assets/img/malware-cnn/exemples_manipulations.png)
_Figure 19. Where each attack strategy injects its payload in a PE file, from Adversarial EXEmples [\[14\]](#ref-14). Partial DOS, padding, and the authors' Full DOS, Extend and Shift manipulations all preserve execution._

![Evasion rate against injected bytes](/assets/img/malware-cnn/kolosnjaji_evasion_rate.png)
_Figure 20. Evasion rate of MalConv as a function of the number of injected padding bytes, from Kolosnjaji et al. [\[13\]](#ref-13)._

A byteplot classifier inherits all of this. Its evidence lives in headers and section boundaries (Figures 12 to 14), which are the parts an attacker can edit without breaking the program. Appended padding shows up as a new band at the bottom of the image, header edits as a change in the first rows, and a section-alignment shift as every band moving down by a fraction of a row; each is a small perturbation in pixel space and the attacks against MalConv transfer with little change. The defence side is younger: byte masking with certified smoothing, which classifies many randomly masked copies of the file and takes a vote, gives a provable bound on how many bytes an attacker must change [\[19\]](#ref-19), at a cost in accuracy and compute.

Arp and colleagues surveyed 30 papers from the top security venues over ten years and catalogued ten recurring pitfalls; sampling bias appeared in 69% of them [\[15\]](#ref-15):

## Where the field is in 2026

**Raw bytes instead of images.** MalConv [\[5\]](#ref-5) embeds each of the 256 byte values into an 8-dimensional vector, so that the network can learn which bytes are similar rather than being told by their numeric value, then applies a 1D convolution with a kernel of 500 bytes and a stride of 500, a gated linear unit, and a global max-pool over the whole file before a small classifier. The stride makes the cost linear in the file length and lets it read two million bytes at once; the max-pool means the decision comes from a few windows, which can be reported back as the regions that triggered it. It removed the wrapping artefact of Figure 4 at the cost of a harder optimization problem. It removed the wrapping artefact of Figure 4 at the cost of a harder optimization problem; the authors note batch normalization hurt and dilated convolutions did not transfer from vision.

![MalConv architecture](/assets/img/malware-cnn/malconv_architecture.png)
_Figure 23. The MalConv architecture, from Raff et al. [\[5\]](#ref-5)._

**Packing-aware training.** ViPER (June 2026) fine-tunes a ViT-B/14 with LoRA and two heads, one for malware and one for packing state, with stratified sampling over the four joint classes so the model sees packed benign and unpacked malicious files in equal measure and cannot use "packed" as a proxy for "malicious". It reports malware ROC AUC 0.926 and packing-detection AUC 0.995 [\[10\]](#ref-10); the gap between those two numbers is a measure of how much easier it is to see that a file is packed than to see what it does. A December 2025 study builds a byteplot detector for packing itself [\[16\]](#ref-16).

**Better layouts.** HilEnT (July 2026) stacks a Hilbert-curve byteplot with two entropy-contrast maps, one against the benign class average and one against the malware average, into a three-channel image [\[6\]](#ref-6):

![HilEnT three-channel image](/assets/img/malware-cnn/hilent_three_channel.png)
_Figure 24. A HilEnT image of a Microsoft BIG 2015 sample: Hilbert layout plus benign and malware entropy channels. From [\[6\]](#ref-6)._

**Honest ablations on a hard benchmark.** On MalNet-Image Tiny, 43 types, a ResNet18 reproduces the published macro-F1 of about 0.65; ImageNet pretraining and light augmentation give the largest gains, a feature pyramid helps calibration more than F1, and schedule-free AdamW reaches the baseline in 10 epochs instead of 96 [\[17\]](#ref-17).

**Datasets with time in them.** EMBER [\[2\]](#ref-2) for static PE features; MalNet [\[3\]](#ref-3) for images at scale; the TESSERACT line [\[11\]](#ref-11), [\[12\]](#ref-12) and the 2025 to 2026 longitudinal Android benchmarks for drift. The 2025 survey of security risks in ML-based detection lays out the pipeline these all sit in [\[18\]](#ref-18).

## A better pipeline, piece by piece

The 2025 and 2026 papers above share a set of design choices, and each one follows from asking what the model should be invariant to and what it should not.

**Deduplicate before you split, with a fuzzy hash.** The test-independence assumption is the one every number rests on. Compute ssdeep or TLSH on the raw binaries, cluster by similarity, and split by cluster; the packing paper's Figure 8 is what that looks like on Malimg [\[8\]](#ref-8). If you only have images, the average hash is a weak substitute and a perceptual hash is a better one. Report the leakage rate of your split next to your accuracy.

**Split by time when you have timestamps.** Train on the past, test on the future, and report the metric per month so a reader can see the decay, which is what AUT summarizes [\[11\]](#ref-11). EMBER ships this split; for family classification without timestamps, the grouped split is the next best thing.

**Do not resize below the byte scale; handle size with the architecture.** A file's width comes from a lookup table, its height from its size, and a 224×224 resize throws away everything finer than a few bytes per pixel. The MalNet-Image Tiny ablation handles the scale variation with a feature pyramid, which lets one network combine coarse and fine feature maps instead of committing to one resolution [\[17\]](#ref-17). Tiling a large byteplot into fixed-size crops and pooling the crop scores is the cheaper alternative.

**Augment with transformations that exist in file space.** Augmentation encodes invariances you believe in. Flipping or rotating a byteplot corresponds to no operation on a file, so it teaches the model an invariance that is false. Appending padding, shifting section alignment, and re-packing correspond to real edits, and those are the augmentations that transfer, which is also why they are the adversary's edits. The same ablation found that lightweight augmentation, Mixup and TrivialAugment, gave one of the two largest gains on MalNet-Tiny [\[17\]](#ref-17).

**Weight the loss, report macro-F1.** Equation (3) with per-class weights, and a metric that counts every family once. Every 2026 paper on an imbalanced benchmark does this; the original tutorial did neither.

**Fine-tune the top, adapt cheaply.** Early ImageNet layers transfer; late ones need to change. Unfreezing the last stage does it for a ResNet; LoRA does it for a ViT by learning a low-rank update to the attention weights, which is what ViPER uses on a ViT-B/14 [\[10\]](#ref-10). The bet behind both is that the shift from photographs to byteplots is small enough to be captured by a few million parameters.

**Give the model the confound as a second target.** If packing is present in 76% of malware and 73% of benign files [\[10\]](#ref-10), a single-head classifier can learn "packed" as a shortcut. A second head that predicts packing state, with sampling stratified over the four joint classes, removes the shortcut by making it useless.

**Add channels that encode what bytes cannot show.** A Hilbert layout fixes the neighbourhood assumption; an entropy channel makes "how compressed is this region" visible at a glance; contrasting the entropy against benign and malicious class averages, as HilEnT does, turns it into evidence [\[6\]](#ref-6).

**Use an optimizer that does not need to know the schedule.** Schedule-free AdamW reached the MalNet-Tiny baseline in 10 epochs where the reference recipe took 96, with no learning-rate schedule to tune [\[17\]](#ref-17). On a benchmark you will retrain many times, that is the difference between an afternoon and a week.

**Cache what does not change.** A frozen backbone's features never change, so compute them once; the whole experiment in this post runs in four minutes because of that. Mixed precision and batched inference are the same idea applied to the parts that do change.

**Plan for the attacker.** Certified byte masking bounds how many bytes an attacker must change to flip the decision [\[19\]](#ref-19); it costs accuracy and compute, and it is the only defence in this list with a guarantee attached.

## Part 2

The next post keeps the CNN and changes the evaluation: MalNet-Image Tiny instead of Malimg, macro-F1 instead of accuracy, a grouped split by default, a size-only baseline reported next to every model, and packed samples held out as a separate test set. The training loop it will use is the one the first version of this post should have used: the last block unfrozen, class-weighted loss, no resize below the byte scale, and the metric computed per family.

```python
from sklearn.metrics import f1_score

net = torchvision.models.resnet50(weights="IMAGENET1K_V1")
for name, prm in net.named_parameters():
    prm.requires_grad = name.startswith("layer4") or name.startswith("fc")   # fine-tune the last block only
net.fc = torch.nn.Linear(2048, n_classes)

counts = torch.bincount(torch.tensor(y[tr]), minlength=n_classes).float()
weights = counts.sum() / (n_classes * counts)          # w_c = N / (C n_c), equation (3)'s correction
loss_fn = torch.nn.CrossEntropyLoss(weight=weights)
opt = torch.optim.AdamW([p for p in net.parameters() if p.requires_grad], lr=3e-4, weight_decay=1e-2)

for epoch in range(epochs):
    net.train()
    for xb, yb in train_loader:                        # 224x224, grayscale replicated to 3 channels
        loss = loss_fn(net(xb), yb); opt.zero_grad(); loss.backward(); opt.step()
    net.eval(); preds, labels = [], []
    with torch.no_grad():
        for xb, yb in test_loader: preds.append(net(xb).argmax(1)); labels.append(yb)
    print(epoch, f1_score(torch.cat(labels), torch.cat(preds), average="macro"))
```

Three choices in that loop do most of the work, and each has a reason. `layer4` is the last of ResNet50's four stages; unfreezing it lets the network re-learn the coarse texture detectors that byteplots need while keeping the early edge detectors from ImageNet. The weight vector makes the two Allaple families count for as much as Skintrim.N in the gradient. And the printed number is macro-F1, computed on a grouped test set, which is the only number in this post that is hard to inflate by accident. If a number in a malware paper is above 95% and the paper does not say how duplicates and time were handled, that is the first question to ask.

## Summary

If you strip the post down to one idea, it is this. A byteplot shows a model the layout of a file: which sections are there, how long they are, what the header says, how the tables are strided. A CNN trained on byteplots learns to recognize layouts, and on a benchmark where every family is one build process run many times, recognizing layouts is enough for 97.3% accuracy. But a nearest neighbour on width and height gets 90.6% on the same benchmark, a nearest neighbour on a 32×32 thumbnail gets 98.0%, and keeping near-duplicates out of the test set leaves accuracy alone while pulling every method's macro-F1 down, which tells you the number was measuring memory. Layout is also the thing that packers rewrite, that drifts as toolchains change, and that adversarial edits can move freely. So the accuracy is real and the ability it suggests, telling malware families apart by what they do, is much smaller than it looks. The way to find that out was not to distrust the number but to put two trivial baselines and one honest split next to it.
